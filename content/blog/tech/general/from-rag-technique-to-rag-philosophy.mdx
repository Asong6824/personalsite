## 引言

今天，几乎所有大模型应用的架构图里都会出现同一个缩写：RAG。它被当作"外挂知识库"的技术方案，被当作解决模型幻觉的工程补丁。但如果只把 RAG 理解成一种技术，我们会错过它背后更深层的东西——一种关于"如何组织智能系统中知识流动"的设计思想。

本文想从 RAG 的工程实现出发，追问三个问题：为什么这个架构必然会出现？它的底层依赖了哪些技术前提？以及——当我们把"检索-增强-生成"这个循环从语言模型身上剥离开来，它还能在哪些地方生根？

## 一、生成能力的跃迁与知识瓶颈

要理解 RAG 为何必然出现，我们需要回溯一条技术主线的演化：机器如何获得理解和生成自然语言的能力，以及这种能力为何最终撞上了知识的瓶颈。

**Word2Vec（2013）** 是一切的开端。Google 的 Mikolov 团队发现，如果把每个词表示成一个高维向量，语义关系会神奇地转化为几何关系。最经典的例子就是：

**king − man + woman ≈ queen**

这个等式不是人为设计的规则，而是从大规模语料中自动学出来的。它的深层含义是：在向量空间里，"男性/女性"的差异和"国王/女王"的差异，指向的是同一个方向。语义不再是被词典定义的死符号，而是可以在空间中滑动、运算的连续量。

想象一个被压缩到二维的向量平面：king 和 queen 相距不远，man 和 woman 也相距不远，而连接 king→man 的箭头，与连接 queen→woman 的箭头几乎平行。royal 的语义被编码在 king 和 man 之间的那段向量里，gender 的语义则被编码在 man 和 woman 之间的那段向量里。

<Word2VecVectorSpace />

这一发现奠定了后续所有技术的基石——从**词向量**到**句子向量**，再到**文档向量**，最终通向 RAG 中的**语义检索**。RAG 之所以能用向量相似度找到相关文档，正是因为 Word2Vec 证明了：意义可以被嵌入空间，距离即相关性。

当然，Word2Vec 只是静态词嵌入，每个词只有一个固定向量，无法区分 "river bank" 和 "bank account" 中的 bank。在随后的几年里，RNN、LSTM、编码器-解码器架构和 Transformer 相继出现，解决了上下文理解和并行训练的问题，为更强大的语言模型铺平了道路。但这些中间步骤的本质，都是让机器更好地"读"和"写"——真正改变游戏规则的，是 GPT 系列对**规模**的探索。

**GPT-1（2018）** 首次验证了"生成式预训练 + 判别式微调"这条路径：先用无标注文本预训练一个语言模型，再针对具体任务做微调。1.17 亿参数的它更像一个概念验证——证明这条路走得通。

**GPT-2（2019）** 将参数扩展到 15 亿，训练数据也从书籍扩展到了数百万网页。一个关键变化出现了：模型开始展现出**零样本能力**——你只需要在输入前加一句 "Translate to French:"，它就能执行翻译任务，无需任何针对翻译的微调。这意味着模型的泛化能力开始超越训练时明确教给它的任务。

然后到了 **GPT-3（2020）**。1750 亿参数，约 5000 亿词的混合语料。量变引发了质变。

| 模型 | 发布时间 | 参数量 | 上下文长度 | 预训练数据量 | 关键能力 |
|------|---------|--------|-----------|------------|---------|
| GPT-1 | 2018.06 | 1.17 亿 | 512 | ~8 亿词 | 预训练 + 微调范式验证 |
| GPT-2 | 2019.02 | 15 亿 | 1024 | ~40GB 网页文本 | 零样本任务泛化萌芽 |
| GPT-3 | 2020.05 | 1750 亿 | 2048 | ~5000 亿词 | 上下文学习、思维链推理涌现 |

GPT-3 展现出了 **上下文学习（In-Context Learning）** 的能力：你不需要微调模型权重，只需要在 prompt 里放几个示例，它就能理解你的意图并给出正确的输出。这里的"示例"可以是零个（Zero-shot，直接下指令）、一个（One-shot，给单个样例）或多个（Few-shot，给少量样例），模型都能从中捕捉任务模式。更惊人的是**思维链推理（Chain-of-Thought Reasoning）**——当你要求模型"一步一步想"时，它真的能展开中间推理步骤，而不是直接跳到一个可能错误的结论。

这些能力并非被明确编程进去的，而是**规模定律（Scaling Laws）**的产物：当模型的参数、训练数据和计算量按幂律增长时，能力会可预测地提升，且在某个临界点后，全新的能力会突然"涌现"出来。

<InContextLearningChart />

从 1.17 亿到 1750 亿，三个数量级的跨越不只是数字游戏——每一次参数跃迁都伴随着能力的质变。GPT-1 证明路线可行，GPT-2 展示泛化潜力，GPT-3 则让" prompt 即程序"成为现实。

这背后有一个核心洞察：**参数即知识**。GPT-3 的 1750 亿个参数里编码的不是单词本身，而是从海量文本中学到的统计规律、事实关联和推理模式。模型出厂时，这些知识已经固化在权重中——你不需要重新训练它，只需要设计正确的 prompt，就能激活参数中沉睡的能力。

这就是 **Prompt Engineering** 的原理：模型已经"知道"了，问题在于你如何用自然语言精确地表达意图并激活它。Prompt 不是 API 那样的确定性接口，而更像一种需要反复调试的"自然语言编程"。

但这里出现了一个根本性的瓶颈：参数知识有三个无法回避的缺陷。第一，**知识截止**——模型只能知道训练数据时间点之前的事；第二，**知识幻觉**——参数化存储是有损压缩，模型会"自信地"编造不存在的事实；第三，**知识更新成本**极高——任何新信息的注入都需要昂贵的重新训练。

当生成能力已经足够强大，而知识的存储方式却成为瓶颈时，工程界的目光自然转向了另一条路径：与其把所有知识塞进参数，不如让模型学会查阅外部资料。

## 二、RAG 的工程本质：检索、增强与生成

### 一个最原始的 RAG：羊肉串问题

假设你问一个大模型："我想买十串羊肉串，要花多少钱？"

大模型不知道你家楼下烧烤摊的价格。它的参数里可能有"羊肉串"这个词，但没有"你家楼下烧烤摊的羊肉串卖 2 元一串"这个具体知识。所以它只能猜："一般来说，羊肉串的价格在 3 到 5 元之间，十串大概 30 到 50 元。"——这是一个看似合理、但实际上可能完全错误的回答。

解决办法很简单：你不需要重新训练模型，只需要在 prompt 里加一句话，"已知一串羊肉串 2 元。"然后再问"十串多少钱？"模型立刻就能准确回答："20 元。"

这就是最原始的 RAG。只不过这里的**检索**（Retrieval）是由你的人脑完成的——你从烧烤摊的价目表上看到了价格；**增强**（Augmentation）是把这条信息写进 prompt 里；**生成**（Generation）是模型基于 prompt 算出总价。RAG 的三个核心环节，在这个极简场景里全部出现了，只是检索环节由人完成。

### RAG 的诞生：从论文到工程

2020 年，Facebook AI Research 的 Lewis 等人在 NeurIPS 上发表了一篇论文——*Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*。这篇论文首次系统性地提出了 **RAG** 这个框架，把预训练的稠密检索器（Dense Passage Retrieval）和预训练的序列到序列生成器（BART）结合起来，做端到端的联合微调。

与此前"先检索、再拼接进 prompt"的简单做法不同，这篇论文的关键创新在于**将检索结果作为生成器的隐状态输入**。检索器召回的文档不是简单地拼在 prompt 前面，而是通过注意力机制深度融合到生成过程中。这意味着模型在生成每一个词时，都在动态地"查阅"外部资料。

实验结果令人印象深刻：在开放域问答（Natural Questions、TriviaQA）和事实验证（FEVER）等知识密集型任务上，RAG 不仅超越了纯参数化的生成模型，也胜过了"检索+拼接"的两阶段基线。这篇论文的价值不只是提出了一种新模型，它证明了一件事：**检索和生成可以作为一个统一的系统来训练，而不是两个割裂的模块**。

此后三年，RAG 从学术研究迅速扩散到工业界。OpenAI 的 ChatGPT 插件系统、LangChain 的 Retrieval 模板、LlamaIndex 的索引框架，本质上都是这篇论文思想的不同工程实现。RAG 不再只是一个模型架构，而变成了一套可复用的系统设计模式。

### RAG 的两面：索引侧与检索侧

如果把一个 RAG 系统比作一家餐厅，**索引侧**就是后厨的备菜流程——采购食材、清洗切配、分类储存；**检索侧**则是前厅的点菜上菜流程——理解客人需求、找到对应菜品、加工呈送。两侧解耦，才能各自优化。

从技术角度看，**索引侧（Indexing）** 负责离线数据准备：原始文档经过清洗、分块、嵌入，最终变成向量数据库中的可检索条目。这是一个"写"的过程，关注的是如何把知识以机器能理解的方式组织起来。

**检索侧（Retrieval / Query）** 负责在线问答生成：接收用户问题，执行查询处理、向量检索、结果重排序，将检索内容与用户问题组装成增强 prompt，最终交由 LLM 生成答案。这是一个"读"的过程，关注的是如何在恰当的时机找到并呈现最相关的信息。

这种划分并非只是为了概念清晰——在工程实践中，两侧的技术栈、优化目标和团队分工往往截然不同。索引侧关心的是嵌入质量、分块策略和存储效率；检索侧关心的是查询改写、召回率和生成效果。理解了这一分野，才能有的放矢地调优一个 RAG 系统。

#### 索引侧：从原始文档到可检索的向量

**① 知识库与索引：价格信息存在哪里？**

羊肉串的价格不能凭空出现，它必须被记录在某个地方——一张价目表、一份菜单、一个数据库。在 RAG 系统中，这叫做**知识库**。真实场景中，知识库可能是产品手册、技术文档、论文库、法规条文，或者企业的内部资料。

但机器不能直接"阅读"原始文档。一篇 PDF 菜单可能包含页眉页脚、排版噪音、扫描图像。所以首先需要做**数据清洗**，去掉无用信息，保留有效内容。然后要做**文档分块**（Chunking），把长篇文档切成小段——比如"羊肉串 2 元/串"就是一个独立的 chunk。接下来，每个 chunk 要通过**嵌入模型**转换成向量，存入**向量数据库**。这样，"羊肉串 2 元/串"就从一个字符串变成了高维空间中的一个点。

#### 检索侧：从用户问题到生成答案

**② 检索：怎么找到正确的 chunk？**

用户问"十串羊肉串多少钱"，系统需要在向量数据库中找到最相关的 chunk。这个过程叫**检索**。

但用户不会总是按标准格式提问。有人可能说"来十个串儿带劲儿的那种多少钱"，有人可能问"烤羊肉串十串价格"。这时候需要**查询处理**——系统会改写用户的查询，用更标准、更丰富的表达去匹配知识库，提升召回正确 chunk 的概率。

检索本身也有多种策略。最基本的**向量检索**是把用户问题也变成向量，找空间中距离最近的 chunk。但纯向量检索可能漏掉关键词精确匹配的场景（比如"2 元"这个具体数字）。所以成熟的系统会采用**混合检索**——同时做向量检索和关键词检索，再把两路结果融合。

**③ 重排序：找到一堆结果，哪个最准？**

检索通常会召回几十个候选 chunk，但它们的相关性参差不齐。有些可能完全无关（比如"烤茄子 8 元"），有些部分相关。这时候需要**重排序**（Reranking）——用一个更精确的模型对候选结果二次打分，把"羊肉串 2 元/串"排在最前面，把无关内容过滤掉。

**④ 增强与生成：把检索结果喂给模型**

找到了"羊肉串 2 元/串"这个 chunk，接下来要把它和用户的问题组合成一个完整的 prompt，这个过程叫**上下文组装**。典型的模板结构是：角色定义 + 已知信息（检索结果）+ 用户问题 + 约束条件。然后 LLM 基于这个增强后的 prompt 生成答案。

不过，检索到的内容未必都相关，全部塞进 prompt 会浪费上下文窗口。所以需要**上下文压缩**——识别并保留关键信息，去掉冗余。此外，系统还可以加入**Few-shot 示例**来引导模型输出格式。

**⑤ 评估：回答得对吗？**

系统上线后，怎么知道它回答得好不好？需要一套**评估体系**。比如**忠实度**（Faithfulness）——答案是否基于检索到的内容？有没有编造？**上下文精确率**（Context Precision）——检索到的 chunk 是否都相关？**答案相关性**（Answer Relevancy）——生成的答案是否切题？

这些指标帮助开发者持续调优——换更好的嵌入模型、调整分块大小、优化查询改写策略。

这个流程并非一成不变——根据业务场景的不同，某些节点可以被裁剪、替换或增强。例如：

- **简单场景**：用户查询 → 向量检索 → 上下文构建 → LLM 生成 → 输出
- **高精度场景**：增加查询改写（HyDE）和重排序（Cross-Encoder）环节
- **混合检索场景**：同时引入向量检索与关键词检索，结果融合后重排

## 三、设计范式的跃迁：从 Prompt Engineering 到 Context Engineering

前面我们把 RAG 拆解为索引侧和检索侧的工程组件，但这是在**静态视角**下观察一个系统的内部结构。如果换一个视角——从**开发者设计思路**的演化来看——RAG 的发展轨迹恰好嵌套在大模型应用设计范式的整体跃迁之中。

这个跃迁经历了三个阶段：Prompt Engineering → Agentic RAG → Context Engineering。每一个阶段的转变，都不仅仅是技术工具的更替，更是"人如何与模型协作"这一根本假设的重构。

### Prompt Engineering 时代：Prompt 即程序

2020 年到 2022 年，大模型应用开发者的核心技能是写 Prompt。

那时候的思考方式是：模型已经预训练好了，它的能力被封存在参数里，问题在于**我如何用一个 prompt 精确地激活它**。开发者像调试程序一样调试 prompt——换措辞、加示例、调顺序、设约束——试图找到那个"能让模型输出正确结果的魔法句子"。

这个阶段的 RAG 系统，本质是 Prompt Engineering 思路的自然延伸：

人负责设计整个检索流程：选什么 embedding 模型、分块多大、召回几个 chunk、怎么拼进 prompt。LLM 在整个流程中完全被动——它既不参与检索决策，也不知道上下文从何而来。检索模块和生成模块之间是单向数据流，LLM 只是最终的消费者。

这背后的设计假设是：**人是系统的设计师，模型是人的工具。** 人把知识整理好，喂给模型，模型负责消化并生成。RAG 的优化目标，也因此被局限在"怎么把检索结果组织进 prompt，让 LLM 理解得更好"。

### Agentic 时代：LLM 成为系统的调度者

2023 年，ChatGPT 的插件系统和 GPT-4 的 Function Calling 能力发布，大模型应用的设计思路发生了第一次质变。

开发者开始意识到：LLM 不只是一个文本生成器，它可以**理解意图、规划步骤、调用工具**。ReAct 框架（Reasoning + Acting）的流行标志着一个新范式的确立——模型可以在"思考"和"行动"之间循环，根据中间结果调整下一步策略。

这个转变对 RAG 的影响是根本性的。

固定管道的 RAG 无法处理需要多轮检索的复杂问题。比如用户问"对比 OpenAI 和 Anthropic 在 2024 年的融资情况"，固定管道只能执行一次检索，要么同时搜两个主题（结果可能都不够深入），要么只能覆盖其中一个。真正合理的做法是先检索 OpenAI 的融资信息，再检索 Anthropic 的融资信息，然后基于两轮结果做对比——但固定管道做不到"看了第一轮结果，决定第二轮搜什么"。

Agentic RAG 的解决思路是让 LLM 自己决定何时检索、检索什么。LLM 不再被动接收上下文，而是通过**工具调用（Tool Call）**主动发起搜索请求。上下文窗口里除了检索结果，还多了**工具列表（Tool list）**和**工具调用记录**——LLM 可以规划多轮检索，根据上一轮的结果决定下一步行动。

检索从"系统预设的流程"变成了"LLM 可调用的工具"。这是一个关键转变：**控制权从人转移到了模型。**

设计假设随之改变：**人设计工具和规则，模型决定何时以及如何使用它们。** 开发者不再手动编排检索流程，而是定义好检索工具的接口，让模型根据任务自主调用。RAG 系统的优化目标也从"怎么组织 prompt"变成了"怎么设计工具接口，让模型能高效地获取信息"。

### Context Engineering 时代：上下文即工作环境

2024 年以来，随着 Claude 的 Artifacts、Cursor 的 Composer、以及各类 AI IDE 的兴起，大模型应用的设计思路进入了第三个阶段。

开发者发现，当 LLM 被赋予越来越复杂的任务时，prompt 本身已经不足以承载任务的完整上下文。模型需要的不只是一段指令，而是一个**持续更新的工作环境**——包含角色定义、可用技能、历史记忆、工具接口、待办事项、中间结果等。

这个范式被称为 **Context Engineering**。它把**上下文窗口（Context Window）**当作一个完整的工作空间来设计，而不仅仅是承载 prompt 的容器。

在这个范式下，上下文窗口被结构化地组织成多个功能区：**系统提示（System prompt）**定义角色和行为规范；**技能文件（Skills YAML）**描述可用的专业能力；**记忆文件（Memory file）**保存跨会话的长期信息；**历史记录（History）**维护对话状态；**工具列表（Tool list）**声明可调用的外部接口；**工具结果（Tool result）**和**检索文档（Docs）**则是动态注入的上下文。

RAG 在这个新范式中的位置也随之改变。它不再是系统中的一个独立模块，而是**上下文管理系统**的一种能力。检索只是 LLM 管理上下文的多种方式之一——除此之外，它还可以加载技能、搜索网页、读取本地文件、唤起长期记忆，甚至执行代码。

对 RAG 系统设计者而言，这意味着优化目标再次发生转移：从"设计一个好的检索流程"到"设计一个好的上下文工作空间"。一个好的 RAG 系统，不是检索精度最高的系统，而是**最懂得在恰当的时机，把恰当的信息，放到恰当的位置**的系统。

回顾这三个阶段，RAG 的每一次重大进化都不是孤立的技术升级，而是大模型应用设计范式转移的缩影。Prompt Engineering 时代，RAG 是人的知识搬运工具；Agentic 时代，RAG 是模型可调用的信息接口；Context Engineering 时代，RAG 是上下文工作环境的信息流管道。变的是控制权的归属和设计的粒度，不变的是那个核心逻辑——**在恰当的时刻，把恰当的信息，放到恰当的位置**。

## 四、RAG 思想的拓展：当"检索-增强-生成"走出聊天框

前面三章，RAG 始终被框定在一个经典场景里：用户提问，系统检索文档，LLM 生成回答。但如果把"检索-增强-生成"这个循环从"问答"的壳子里抽离出来，它的适用范围远不止于此。

这一章我们来看三个产品——NotebookLM、Obsidian + Claude Code、以及 LLM Wiki。它们形态各异，甚至不会自称"RAG 系统"，但底层都遵循同一个设计思想：**找到正确的信息，用合适的方式增强它，然后生成有价值的内容**。它们的差别在于：各自改写了 RAG 循环中的某一个变量。

### NotebookLM：RAG 的听觉化

NotebookLM 是 Google 推出的 AI 研究助手。用户上传文档、网页或幻灯片，系统构建知识库，然后 AI 生成一段双人播客对话——两个 AI 主持人以自然聊天的方式"讲解"你的资料。

它的 RAG 基因非常清晰：从你上传的文档中**检索**相关内容，**增强**为播客对话的素材，**生成**一段有节奏、有情绪的叙事音频。但 NotebookLM 的创新在于，它改写了"生成"这个环节的定义。

传统 RAG 的生成物是**答案**——准确、简洁、直接回应问题。NotebookLM 的生成物是**叙事**——有铺垫、有转折、有互动感的对话。这意味着系统对检索到的内容有更高的要求：不仅要"相关"，还要"可讲述"。一个数据点如果被检索出来，却无法融入一个自然的对话弧线，就会被舍弃或改写。

更深一层，NotebookLM 还改写了"用户角色"。在传统 RAG 中，用户是提问者；在 NotebookLM 中，用户是**听众**。系统不需要等待用户输入，而是主动基于知识库生成内容。这暗示了一种新的 RAG 形态：**推送式生成**——系统基于预置的知识库主动产出内容，而非被动响应查询。

### Obsidian + Claude Code：个人知识库的主动智能

Obsidian 是一款本地优先的笔记软件，以双向链接和知识图谱著称。Claude Code 是 Anthropic 推出的 AI 编码助手，可以在代码库中读取文件、执行命令、迭代修改。当两者结合，一个独特的 RAG 变体出现了。

Obsidian 的笔记库——那些日积月累的项目文档、读书笔记、灵感碎片——变成了知识库。但与企业的标准化文档库不同，这个知识库是**高度个人化的**：它的组织方式反映了一个人的思维模式，它的链接结构是一个人的知识图谱，它的命名习惯甚至带着个人的记忆线索。

Claude Code 的介入改变了 RAG 的触发方式。传统 RAG 是**请求-响应**模式：用户主动提问，系统被动回答。而在 Obsidian + Claude Code 的 workflow 中，检索是**嵌入式**的——你在写代码、写文档、做决策时，AI 在旁持续感知你的知识库，在恰当的时机介入。你不需要问"我三个月前关于这个架构的笔记在哪里"，AI 会在你写代码时自动引用那段笔记。

这里的"增强"也不再是把 chunk 拼进 prompt 那么简单。Claude Code 需要理解 Obsidian 笔记之间的链接关系、标签体系、以及时间线——这不是平面化的文档检索，而是在一个**个人知识图谱**中导航。生成物也不是回答，而是**辅助完成一项任务**——写一段代码、补全文档、或者帮你梳理思路。

### LLM Wiki：集体知识管理的生成式重构

Wiki 是互联网最古老的知识组织形式之一——人写、人读、人维护。但传统 Wiki 有一个结构性困境：**知识在增长，但关联在衰减**。条目越来越多，交叉引用越来越难以维护，新人越来越难从 Wiki 中建立起完整的知识图景。

LLM Wiki 尝试用生成式 AI 重构这个循环。它的核心假设是：Wiki 不应该只是静态的知识存储，而应该是**动态的知识生长系统**。

在这个系统中，RAG 的三个环节被重新分配了角色：

- **检索**不再只服务于读者的查询，还服务于系统自身的"理解"。LLM 持续扫描 Wiki 的全局内容，识别知识之间的隐性关联——哪些条目其实在讲同一件事？哪些概念在不同条目中被重复定义？哪些链接已经失效或指向了过时的内容？

- **增强**的核心是**关联推理**。LLM 不仅读取单个条目的内容，还理解它在整个知识网络中的位置。当一个新条目被创建时，系统能自动建议应该链接到哪些现有条目；当某个概念发生变化时，系统能识别出所有受影响的条目并提示更新。

- **生成**则体现在两个方面：一是**自动补全**——基于已有内容生成新条目的初稿或摘要；二是**知识整合**——当多个条目之间存在冗余或矛盾时，系统生成整合建议，由人来裁决。

与传统 RAG 最大的不同在于：LLM Wiki 中的"检索"是**双向**的。人检索 Wiki 获取知识，同时 LLM 也在"检索"Wiki 以维护其结构完整性。知识库不再是被动的客体，而是与 AI 共同演化的有机体。

### 三个变体，一条主线

把这三个产品放在一起，可以清楚地看到 RAG 思想如何在不同场景中被改写和拓展：

| 维度 | NotebookLM | Obsidian + Claude Code | LLM Wiki |
|------|-----------|----------------------|----------|
| 知识库 | 用户主动上传的文档集 | 个人持续积累的笔记网络 | 集体维护的百科条目 |
| 检索触发 | 生成前自动执行 | 嵌入工作流持续感知 | 双向：人查询 + 系统自检 |
| 增强逻辑 | 叙事组织与情绪设计 | 个人知识图谱的上下文理解 | 全局关联推理与结构维护 |
| 生成物 | 叙事化音频播客 | 代码/文档/决策辅助 | 条目草稿、整合建议、关联更新 |
| 用户角色 | 听众（被动接收） | 协作者（共同完成任务） | 编辑者（裁决与确认） |

它们都没有把自己包装成"下一代 RAG 系统"，但底层共享着同一个核心洞见：**任何智能系统的输出质量，都受限于它能在多大程度上获取和利用正确的信息**。NotebookLM 把这个洞见应用到了内容创作，Obsidian + Claude Code 应用到了个人工作流，LLM Wiki 应用到了集体知识管理。

RAG 的边界在扩大，但它的核心逻辑从未改变——只是现在，"恰当的信息"可以是一段适合讲述的故事，"恰当的位置"可以是一个正在进行中的工作流，"恰当的时刻"可以是系统自主判断的维护周期。
