pi 是一个极简的 Agent 运行时，它包含统一的 LLM API、智能体循环、终端用户界面和编码智能体命令行工具。
pi 在技术圈内获得了极高的评价，被很多人推荐作为agent的底座。今年年初火爆的 openclaw，就使用 pi 作为自己的 Agent Loop。
对于喜欢折腾，自己动手的极客来说，Pi是他们

## pi 的诞生
pi 的作者是 Mario Zechner，这是一个德语区名字，中文翻译应该是马里奥·泽克纳（就是那个顶蘑菇的马里奥，只不过顶蘑菇这个的名字来源是西雅图的房地产商）。

Mario 居住在奥地利。2009 年，他因为想写 Android 游戏，开始做一个名为 AFX 的 Android 游戏框架；后来为了让开发和调试更方便，把它扩展成可在桌面和移动端共享代码的跨平台框架，这就是后来的 libGDX。

从 2023 年开始，他和我们一样，开始使用大模型编码。他最初从浏览器手动复制代码，后来他开始使用 cursor。2025 年 4 月，Peter Steinberger（没错，就是 openclaw 的作者）和他说：兄弟，这些编程 agent 现在真的能用了。

在接下来的一个月，他沉浸在各种编程工具中，他自己说他那段时间没怎么睡过觉，做了很多东西，但是都没什么用。这时候他受够了这些编程 agent，他在想自己做一个能有多难，这时 Peter 说，我做一个私人助手就行。现在我们都知道 Peter 后面的故事了。

这篇文章的主角是 Mario 和 pi，所以让我们把视角拉回来。

Mario 最初一直很喜欢 Claude Code。他认为 Claude Code开创了一种新的品类：训练模型使用工具，然后用 Bash 工具探索代码库，直接找到需要的地方去理解，然后修改代码，这也是他 2025 年 4 月直接不睡觉的原因。

渐渐地，他觉得 Claude Code 变得像 Homer 的那辆汽车一样，塞了过多无用的东西进去，他实际用到的功能可能还不足 10%。他把 Homer 的汽车和 Claude Code 都称为宇宙飞船，他不想要一辆 Homer 的汽车，也不想要宇宙飞船。

Mario 思考出两个论点

一是我们还处在摸索和试错的阶段，没有人知道完美的 coding agent 应该长什么样

二是我们需要一个更好的方式去探索 coding agent，它们应该自我修改，快速验证

所以，一个冲着 Claude Code 大吼大叫的老头会怎么做呢？他会自己写一个编码代理程序，然后取一个谷歌搜不到的名字，这样就永远不会有用户。这意味着GitHub问题跟踪器上也永远不会出现任何问题。

## pi-coding-agent 总览

作为一个 coding agent，pi-coding-agent 的交互方式与 claude code、codex 几乎相同，包括

 - 跨系统，可以在 Windows、Linux、MacOS 以及任何具有 Node.js 运行时的系统
 - 支持多大模型提供商，可以在对话中切换
 - 会话管理，支持继续、恢复和分支
 - 支持加载项目上下文文件（agent.md）
 - 支持 / 命令
 - 支持 skill
 - 通过 json 或 RPC 进行无头操作

正如 Mario 自己说的，他受够了 Claude Code 宇宙飞船般的功能，所以 pi-coding-agent 的设计哲学是只保留最小可用，因此：

1. 默认 yolo 模式
2. 没有内置 TODO
3. 没有计划模式
4. 不支持 MCP
5. 不支持 subagent

Mario 自己说他在使用 claude code 时，即使使用安全模式，也不看具体执行了什么命令，只是一味地摁 enter，所以他干脆把 pi-coding-agent 设计成了默认 yolo 模式。

加载 MCP 通常会占用 10k 至 20k 的 token，对于大多数模型 128k 到 256k 的上下文长度来说，仅加载 MCP 就占据了 10% 上下文长度。而很多 MCP 在对话中用不到。

他在博客中写得非常硬：Pi “does not and will not support MCP”。他的主要理由不是讨厌协议本身，而是认为 MCP 对多数 coding-agent 场景过重，尤其是 context overhead 太大。

他的替代方案是：CLI tools + README。也就是把外部能力做成普通命令行工具，配一个说明文档；agent 需要时再读 README，再用 bash 调用工具。这是 progressive disclosure：需要时才付 token 成本，而且天然可组合、可管道化、容易扩展。

所以他不是说“外部工具集成不好”，而是说：MCP 作为默认工具注入机制太臃肿；Unix CLI 更符合 Pi 的极简 harness 设计。

他同样不想内置 dedicated sub-agent tool。核心反感点是 可观察性差 和 上下文转交不透明。他批评 Claude Code 这类系统里，主 agent 生成子 agent 后，用户看不到子 agent 到底读了什么、怎么推理、错在哪里；他说这是 “black box within a black box”。Mario Zechner 的博客

更深一层，他认为很多人用 subagent 做 context gathering，是工作流设计问题。为了节省主会话 context 而在中途派子 agent 搜上下文，他觉得这说明前期没有规划好。更好的方式是：先开一个独立 session 做 context gathering，产出一个 artifact，比如 context.md、调研笔记、设计文档，再在干净的新 session 里把这个 artifact 交给 agent。

但他并不是彻底否定 subagent。他承认有合理场景，尤其是 code review。他的做法也很 Pi：不是内置 subagent primitive，而是让 Pi 通过 bash 再启动一个 pi --print，用 slash command 包一层。也就是说：如果要子 agent，就把它当成另一个可观察、可保存、可单独进入的 Pi 进程，而不是隐藏在主 agent 内部的机制。

他还明确反对“开多个 subagent 并行实现多个 feature”这种玩法，认为这在真实代码库里容易把质量搞坏。

我们不评价重剑无锋和瑞士军刀哪个更好用，只来学习一下 pi 是怎么做的

### 最小系统提示词

```
You are an expert coding assistant. You help users with coding tasks by reading files, executing commands, editing code, and writing new files.

Available tools:
- read: Read file contents
- bash: Execute bash commands
- edit: Make surgical edits to files
- write: Create or overwrite files

Guidelines:
- Use bash for file operations like ls, grep, find
- Use read to examine files before editing
- Use edit for precise changes (old text must match exactly)
- Use write only for new files or complete rewrites
- When summarizing your actions, output plain text directly - do NOT use cat or bash to display what you did
- Be concise in your responses
- Show file paths clearly when working with files

Documentation:
- Your own documentation (including custom model setup and theme creation) is at: /path/to/README.md
- Read it when users ask about features, configuration, or setup, and especially if the user asks you to add a custom model or provider, or create a custom theme.
```

https://cchistory.mariozechner.at/

claude code 的系统提示词细致地涵盖了角色定位、任务领域、安全边界、工具和交互风格

与之相比 pi-coding-agent 只说明角色和可以使用的工具，claude code 在系统提示词要花费 10000 token，而 pi-coding-agent 只需要不到 1000。

如此简单的系统提示词难免让人怀疑 pi-coding-agent 能否正常完成编码任务。

测试结果表明，因为模型大多针对代码类任务进行过强化学习训练，所以只需要简单地表达你是一个专业的编码助手，大模型就可以激活相应的能力。
